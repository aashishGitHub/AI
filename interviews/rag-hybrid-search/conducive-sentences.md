# RAG & Hybrid Search — Conducive Sentences (prose retelling)

> Plain-English narration of the whole topic, section bridging to section. Read this to *talk* fluently, not just recall facts. Pairs with [`answers.md`](answers.md).

---

**Start with what RAG buys you.** A bare language model only knows what was in its training data, so it can't answer from your private, current documentation, and when it doesn't know something it tends to make it up. Retrieval-augmented generation fixes this by adding a retrieval step: you fetch the most relevant passages from your own corpus and hand them to the model as context, so the answer is grounded in current, citable, private knowledge — and updating that knowledge is a re-index, not a retrain. That's why you reach for RAG when the knowledge is large and changing, for fine-tuning when you need to change the model's *behavior* or style, and for a giant context window only when the whole corpus is small and static.

**The single most important thing to say is that RAG is two paths, not one.** There's a write path that turns a messy corpus into searchable vectors, and a read path that turns a user's question into a grounded answer, and they only touch at the store. What makes the split matter is that the two paths have opposite constraints: the write path is throughput-bound and allowed to be slow — Ask AI runs it weekly and nobody is waiting — while the read path is latency-bound because a user is literally watching tokens appear. Keep them separate and you can scale and debug each on its own; blur them and you optimize the wrong things. The split is also your debugging map: a bad answer is either a write-path fault, a read-path retrieval fault, or a generation fault, and naming which one comes first.

**Walk the write path and you see where quality is actually won.** Ask AI fetches HTML from an S3 bucket, strips the headers, footers, and sidebars, chunks each page to no more than a thousand tokens, embeds every chunk with a small OpenAI embedding model into 1,536-dimensional vectors, and stores them in Couchbase. Cleaning isn't cosmetic — navigation and boilerplate repeat on every page, so if you embed them, thousands of chunks cluster around chrome instead of content and your keyword search matches the same junk everywhere. And chunking is the highest-leverage, cheapest knob in the whole system: chunks too big dilute a vector across several ideas so the right passage never scores high, chunks too small split an answer across fragments, and structure-aware chunking that respects headings fits documentation beautifully because the author already segmented the meaning for you.

**Freshness sounds like a speed problem but it's really a versioning problem.** The corpus changes, so you re-embed on a schedule, but the operation that takes a system down is mutating the live index in place and half-failing — now sixty percent of your chunks are new and forty percent are stale or missing, and nothing throws an error. The correct pattern is to build the new version beside the old one, validate it, and only then flip the query path over atomically, keeping the old version as a backup. That's exactly what the design doc means when it lists "backup for old vector embeddings" and "validate the newly created embeddings" as requirements. Parallelism — Ask AI's ten goroutines cutting the job from five or six hours to about twenty minutes — is a throughput win *inside* that safe pattern, not a replacement for it.

**Embeddings deserve a moment because they're a shared contract between the two paths.** An embedding maps text to a vector so that similar meaning becomes geometric closeness, and cosine similarity compares direction rather than magnitude, which keeps long and short chunks comparable. The non-negotiable rule is that the query and the documents must be embedded by the *same* model, or their vectors live in different spaces and "nearest" means nothing. This is why swapping the embedding model is a full corpus migration: you re-embed everything, build a new versioned index, and switch the query-side embedding at the same instant you switch the index. It's also why retrieval sometimes degrades after an "unrelated" library upgrade — the embedding stage shifted underneath you, so pin and version it like any dependency.

**Now the retrieval decision that defines this topic: why hybrid beats pure vector.** Dense vector search matches meaning, so it finds performance docs for "make my database faster" even without the word "faster." Sparse full-text search matches exact tokens, so it finds an error code, an API name, or a SQL++ keyword that vector search would paraphrase right past. Each fails exactly where the other wins, and documentation is full of exact identifiers, which is the class of query that pushed Ask AI from pure vector to hybrid. Running both and fusing recovers the keyword-precise questions without losing semantic recall. The subtlety is that cosine scores and BM25 scores aren't on the same scale, so you fuse on rank with something like Reciprocal Rank Fusion, or you normalize and weight — and Ask AI does both searches in a single Couchbase query for one low-latency round trip, falling back to pure vector when hybrid returns nothing so a paraphrase-only query never comes back empty.

**Retrieval gets you candidates; re-ranking gets you the right five.** Initial retrieval runs an approximate nearest-neighbor search over the whole corpus, tuned for cheap recall with coarse scores, so you retrieve wide — say the top twenty to a hundred — and then spend real ranking effort only on that shortlist, because only the top K ever enter the prompt. Ask AI's re-ranker is a heuristic: the base hybrid score plus a preference for medium-length chunks plus bonuses for code, headings, and structured content. It's cheap, fast, transparent, and domain-aware, and its weakness is fragility — hand-tuned weights don't transfer and a bonus can outrank true relevance — so the discipline is to ablate each term against an eval set and prove it earns its place. A cross-encoder, which scores the query and document jointly, is more accurate but costs a model pass per candidate, so if you adopt one you bound the cost by re-ranking a small shortlist, distilling the model, caching, and degrading to the heuristic under load. K itself — five for Ask AI — is an eval-tuned parameter: too low starves grounding, too high inflates cost and buries the signal in the middle of the prompt.

**Before any of that retrieval runs, you fix the query.** Multi-turn questions are full of pronouns and ellipsis — "and for the paid tier?" is meaningless to an embedding model — so Ask AI rephrases the query against the chat history into a self-contained form before embedding it. Crucially, it uses a deliberately lightweight LLM call for this, not a second large one, because the goal is to cheaply repair the query and a big second call would roughly double cost and latency for little extra gain. When you need more recall on hard queries you can reach for query expansion, HyDE, or multi-query, but each adds latency and cost and should be justified on an eval set rather than added by reflex.

**Then generation, where perfect retrieval can still fail.** You build the prompt with the behavior rules in the system message — answer only from the context, cite the source URLs, and say "I don't know" when the context is weak — followed by the K chunks with their source URLs, followed by the rephrased question. Because models attend most to the beginning and end of a long context and under-use the middle, you keep K tight and put the strongest chunks at the edges. You enforce grounding not just by instruction but by gating on retrieval confidence so weak context yields an honest refusal instead of a fluent hallucination. And you stream the answer over SSE, which doesn't change correctness but transforms perceived latency, at the cost of handling mid-stream failures and tracking time-to-first-token. When the right chunk is ranked first and the answer is *still* wrong, that's a generation fault — the prompt contract, the chunk ordering, or the model trusting its own memory over your context.

**Finally, the staff-level view: scale each path, and know when to stop.** The write path scales with corpus size through parallel batch embedding; the read path scales with query volume through store replicas, ANN tuning, caching, and model or K choices — and their capacity plans share nothing. Freshness versus cost is an explicit decision between a simple weekly full re-embed and an incremental, event-driven pipeline that only embeds the deltas. Multitenancy demands hard data isolation so one tenant's chunks never surface in another's retrieval, plus per-tenant rate and token limits — which Ask AI threads through the iQ Backend, where every call carries a Tenant and User ID and free versus paid tiers get different caps. The real mark of seniority is knowing when hybrid and re-ranking *aren't* worth it: a tiny static corpus might be better served by long context, a purely semantic query mix might not need full-text, and any complexity that doesn't move the number on your eval set is just latency and operational cost. Which is why this topic is inseparable from evaluation — you only earn the right to add a re-ranker or raise K by showing the metric moved.

# Frontend supply-chain security: dependencies, lockfiles, SRI and third-party scripts
**Round:** 11 · Frontend Security · **Level:** Lead / Staff · **Time:** 12 min · **Tags:** supply chain · dependencies · npm
Source: https://whetstone-v1.vercel.app/#security

Scenario: a popular npm dependency is compromised and its post-install script runs in your CI. Reduce likelihood and blast radius.

## What they're really testing
Can you split the problem into build-time (CI/dev machines) and run-time (users' browsers) attack surfaces, and propose prevention, containment, detection and an incident playbook?

## Core answer (key points)
- **Two blast radii:**
  - *Build time:* install/lifecycle scripts run with CI secrets, network, and write access to artifacts.
  - *Run time:* code bundled into the app runs with your origin's privileges in every user session.
- **Reduce exposure:** fewer deps; prefer well-maintained ones; replace one-liner packages; review new transitive deps in lockfile diffs.
- **Pin and reproduce:** commit lockfiles; CI uses `npm ci` / `pnpm install --frozen-lockfile`; lockfile changes get reviewed like code.
- **Cooldown on new versions:** let a release age a few days before adoption (Renovate `minimumReleaseAge`), because many malicious versions are detected and unpublished quickly.
- **Disable install scripts by default:** `ignore-scripts=true`, or pnpm's explicit allowlist (`onlyBuiltDependencies`) for packages that genuinely need builds. (Exact config keys change between pnpm majors; verify.)
- **Provenance:** prefer packages with npm provenance attestations; publish your own from CI with provenance (SLSA levels as a framework).
- **Least-privilege CI:** short-lived, scoped tokens (OIDC to cloud), secrets not exposed to install steps, publish only from protected workflows, isolated runners.
- **Behavioural scanning:** advisories (Dependabot/npm audit) catch known CVEs; behaviour tools (Socket-style) flag new install scripts, network or filesystem access, obfuscation.
- **Third-party scripts (runtime):** inventory with owners; remove unused; SRI (`integrity` hash) for versioned static CDN files; self-host where possible; CSP to constrain; sandbox in iframes or workers (Partytown) when feasible; restrict tag-manager publish rights; monitor CSP reports and outbound requests in RUM.
- **SRI limitation:** useless for scripts whose content changes at the same URL (tag managers, "latest" loaders).
- **Incident playbook:**
  1. Identify affected versions and where they ran (CI logs, dev machines, shipped bundles).
  2. Pin/override to a clean version (`overrides`/`resolutions`), rebuild, redeploy.
  3. Rotate every secret the compromised code could have read (CI tokens, npm tokens, cloud creds).
  4. Assess what shipped to users; invalidate sessions if runtime exfiltration was possible.
  5. Postmortem: which control would have caught it.

## Mental model / flow
```
            BUILD TIME                                   RUN TIME
registry ─► install (scripts?) ─► build ─► artifact ─► CDN ─► user browser
   │cooldown   │ignore-scripts      │lockfile review         │CSP / Trusted Types
   │provenance │scoped CI secrets   │SRI for 3rd-party       │tag governance
   └── scanners (advisory + behaviour) ─────────────────────► CSP reports / RUM
                         incident ─► pin/override ─► rotate secrets ─► audit shipped code
```

```html
<!-- SRI on a pinned CDN asset; hash generated by your build, not copied -->
<script src="https://cdn.example.com/widget@3.1.0/widget.min.js"
        integrity="sha384-<base64-digest>" crossorigin="anonymous"></script>
```

## Trade-offs & pitfalls
- `ignore-scripts` breaks packages with native builds (esbuild, sharp, etc.); maintain an allowlist.
- Cooldown delays security patches too; allow fast-track for advisory fixes.
- `npm audit` noise (dev-only, unreachable paths) leads teams to ignore it; triage by reachability.
- Lockfile diffs are huge; tooling that summarises "new packages / new maintainers / new scripts" makes review real.
- Tag managers let non-engineers ship arbitrary JS to production; that's a governance problem more than a technical one.

## Likely follow-ups
- *Typosquatting / dependency confusion?* Scope internal packages, configure registry per scope, block public fallbacks for internal names.
- *Vendoring?* Raises review burden; useful for tiny critical deps.
- *SBOM?* Generate per build (CycloneDX/SPDX) so "are we affected?" is a query, not a hunt.
- *Monorepo with many apps?* Central Renovate config, shared allowlist, one dependency policy owner.

## Say it in 60 seconds
There are two blast radii: CI and dev machines, where install scripts run with secrets, and users' browsers, where bundled code runs with our origin's privileges. To reduce likelihood: fewer dependencies, committed lockfiles with `npm ci`, reviewed lockfile diffs, and a cooldown before adopting new releases since most malicious versions get pulled fast. To contain: install scripts off by default with an allowlist, scoped short-lived CI credentials, provenance on what we consume and publish, and CSP plus Trusted Types at runtime. Third-party tags get an inventory, owners, SRI where content is versioned, sandboxing where possible and restricted tag-manager rights. Detection is advisories plus behaviour scanning plus CSP reports. When it hits: override to a clean version, redeploy, rotate every exposed secret, and audit what shipped.
